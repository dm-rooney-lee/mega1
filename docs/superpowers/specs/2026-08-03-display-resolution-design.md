# 화면 선명도 개선 설계 (해상도 파이프라인 재구성)

작성일: 2026-08-03 · 브랜치: `fix/display-resolution`

## 무엇을 왜 고치나

레티나 화면에서 게임이 흐릿하게 보인다. 원인은 하나다: **캔버스가 실제로 그리는 픽셀 격자(백킹 버퍼)가 화면의 물리 픽셀보다 훨씬 작다.**

지금은 버퍼가 960×540으로 고정돼 있고, 브라우저가 그것을 창 크기에 맞춰 늘린 뒤 다시 화면 배율만큼 늘린다. 맥 레티나에서 창이 1512×900이면 최종적으로 3024×1701개의 물리 픽셀을 채워야 하는데, 실제로 그려진 것은 51.8만 픽셀뿐이다 — **약 10배를 늘려서 채우고 있다.**

고치면 다음이 달라진다.

| 지금 보이는 문제 | 고친 뒤 |
|---|---|
| 전체가 흐릿함 | 버퍼가 물리 픽셀과 1:1 → 늘리는 단계가 사라짐 |
| 글자가 뭉개짐 | 글자를 화면 실해상도로 직접 래스터화 |
| 움직일 때 경계가 지글거림 | 배율이 정수가 아니어도 어긋남이 생기지 않음 |
| 원·대각선이 계단처럼 거침 | 최근접 이웃 확대를 끄고 매끄럽게 |
| 위아래 검은 띠 | 창을 꽉 채움 (아주 넓은 창에서만 얇은 좌우 띠) |

## 왜 이 방식인가 — 코드로 확인한 제약

이 설계는 추측이 아니라 설치된 Phaser 4.2.1 소스와 이 저장소의 레벨 데이터를 직접 확인해서 나왔다.

1. **Phaser 4는 화면 배율을 전혀 모른다.** 배포 번들 전체에서 `devicePixelRatio`는 단 한 번, 값을 기록하는 데만 쓰인다. 화면 크기 설정에는 `resolution` 같은 항목이 아예 없다.
2. **캔버스 버퍼 크기는 게임 크기와 항상 같다.** 설정의 `zoom`은 CSS 표시 크기만 바꾼다. 따라서 버퍼를 키우는 유일한 방법은 게임 크기 자체를 키우는 것이고, 그러면 게임 좌표계가 함께 커진다 → **카메라 배율로 되돌려야 한다.**
3. **세로는 540으로 고정해야 한다.** 8개 스테이지 전부 세로 540이고, 7스테이지는 천장을 y=0에 두어 위아래 여유가 0이다. 세로를 늘리면 월드 밖이 보인다.
4. **Phaser 4의 새 `EXPAND` 모드는 쓸 수 없다.** 창이 16:9보다 세로로 길면 논리 *세로*를 늘리는 방향으로 동작한다 — 3번과 정면으로 충돌한다.
5. **히트박스는 스프라이트 배율에 연동된다.** 움직이는 물체의 몸체 크기는 `원본 크기 × 스프라이트 배율`로 계산된다. 반면 고정된 지형의 몸체 크기는 배율과 무관한 절대값이다. → 스프라이트 배율을 건드리는 작업은 움직이는 물체(플레이어·적·기어·진자·튀어나오는 가시)에만 영향을 준다.

외부 조사로도 같은 결론을 확인했다: Phaser에서 레티나를 지원하는 정석은 "화면 배율 모드를 끄고, 게임 크기를 배율만큼 키우고, `zoom`을 배율의 역수로 두고, 창 크기 변화를 직접 처리한다"이다.

## 어떻게 동작하나

핵심은 **세 가지 크기를 분리**하는 것이다.

```
논리 좌표 (게임 로직이 쓰는 단위)      세로 540 고정, 가로 854~1100 가변
        │  카메라 배율 Z = 버퍼세로 / 540
        ▼
백킹 버퍼 (실제로 그리는 픽셀 격자)     창CSS크기 × 화면배율  ← 물리 픽셀과 1:1
        │  CSS 배율 = 1 / 화면배율
        ▼
CSS 표시 크기 (창을 꽉 채움)            창 크기와 동일
```

레벨 데이터·중력·이동 속도·타일 크기는 **전부 논리 좌표 그대로** 쓴다. 즉 게임플레이 수치는 한 줄도 바뀌지 않는다.

### 계산 예 (창 1512×900, 화면 배율 2)

| 값 | 계산 | 결과 |
|---|---|---|
| 버퍼 | 1512×2, 900×2 | 3024 × 1800 |
| 카메라 배율 Z | 1800 / 540 | 3.333 |
| 논리 가로 | 3024 / 3.333 | 907 (범위 안 → 띠 없음) |
| CSS 표시 | 3024/2, 1800/2 | 1512 × 900 (창을 꽉 채움) |
| 물리 픽셀 대비 | 3024×1800 vs 3024×1800 | **1 : 1** |

### 구성 요소

**1. 화면 계산 (신규 `src/display.ts`)**

브라우저 API를 만지지 않는 순수 함수. 창 크기와 화면 배율을 받아 위 표의 값을 계산한다. 이 저장소의 `pure-logic-testing` 규칙에 맞게 단위 테스트로 검증한다.

- 화면 배율은 3까지만 인정한다(그 이상은 버퍼가 지나치게 커져 성능만 깎인다).
- 논리 가로는 854~1100으로 제한한다. 이유는 아래 "고려사항" 참조.
- 제한에 걸리면 남는 공간은 좌우 띠로 처리한다(세로 띠는 절대 만들지 않는다).

**2. 게임 설정 (`src/main.ts`)**

- 화면 배율 모드를 끄고, 크기를 계산된 버퍼로 지정, CSS 배율을 화면 배율의 역수로 지정.
- `pixelArt` 설정을 제거한다. 이 설정은 최근접 이웃 확대를 강제해서 지금 문제의 절반을 만들고 있다. 게임의 그림이 실제 픽셀아트가 아니라 원·둥근모서리·삼각형으로 그려진 도형이라 이 설정이 오히려 해롭다.
- 대신 매끄러운 확대를 켠다.

**3. 창 크기 변화 처리**

창이 바뀌면 버퍼와 카메라 배율을 다시 계산해 적용한다. 카메라 크기는 Phaser가 자동으로 맞춰주지만 **배율은 자동으로 갱신되지 않으므로 직접 다시 넣어야 한다.**

**4. 플레이 화면 HUD (`src/scenes/GameScene.ts`)**

카메라를 확대하면 화면에 고정된 표시물도 함께 확대·이동한다. 별도 카메라나 별도 씬을 만들지 않고, **카메라가 현재 보고 있는 영역**을 기준으로 매 프레임 위치를 다시 잡는다. 표시물은 4개(조작 안내, 실드 표시, 스테이지 표시, 스테이지 이름)뿐이라 비용이 없다.

글자는 카메라 배율만큼 확대되므로, 글자의 내부 래스터 해상도를 그 배율로 올려 선명하게 만든다.

**5. 제목·게임오버·클리어 화면**

월드가 없으므로 카메라 배율을 건드리지 않는다. 좌표계가 버퍼 픽셀이 되므로, 중앙 정렬을 실행 시점의 화면 크기 기준으로 바꾸고 글자 크기에 UI 배율을 곱한다. 이 세 화면의 글자는 애초에 버퍼 해상도로 그려지므로 별도 처리 없이 선명해진다.

**6. 문서 페이지 (`index.html`)**

최근접 이웃 확대 지정을 없애고, 캔버스가 창을 채우도록 한다.

### 그림 선명도 (2단계)

위까지 하면 글자와 화면 전체는 물리 픽셀과 1:1이 되지만, **스프라이트 그림은 여전히 원본 크기로 만들어진 텍스처를 카메라가 확대해서 보여준다.** 매끄럽게 확대되므로 지금의 거친 계단은 사라지지만 약간 부드럽게 번진다.

완전히 선명하게 하려면 텍스처를 처음부터 크게 만들고 스프라이트를 그만큼 줄여야 한다. 이때 위 제약 5번 때문에 **움직이는 물체의 몸체 크기를 같은 배수로 보정해야 한다**(플레이어·적·기어·진자·튀어나오는 가시, 그리고 가시 타일). 고정 지형은 보정이 필요 없다.

이 부분은 히트박스를 건드리므로 **1단계와 분리해서 진행하고, 몸체 크기가 변하지 않았음을 단위 테스트로 못 박은 뒤에만 반영한다.** 검증에 실패하면 2단계는 되돌리고 1단계만 남긴다.

## 완료조건

측정 가능한 기준. 모두 실제 브라우저에서 확인한다.

1. 캔버스의 `width`/`height`가 `창 CSS 크기 × 화면 배율`과 정확히 일치한다.
2. 캔버스의 CSS 크기가 창 크기와 일치한다(계산된 논리 가로가 제한 범위 안일 때 띠가 0).
3. 카메라가 보는 세로 범위가 정확히 540 논리 단위다.
4. 창 크기를 바꾼 뒤에도 1~3이 유지된다.
5. 게임 화면의 HUD 4개가 화면 안쪽 원래 자리(왼쪽 위, 오른쪽 위, 중앙 상단)에 있다.
6. 콘솔 오류가 없다.
7. `npx tsc --noEmit` 통과, `npm test` 전부 통과.
8. 플레이어가 이동·점프·낙사·적 밟기를 정상 수행한다(히트박스 회귀 없음).
9. 2단계까지 갔다면: 움직이는 물체의 몸체 크기가 이전과 동일함을 단위 테스트가 보장한다.

## 금지사항

- 중력·이동 속도·점프 세기·타일 크기·레벨 좌표를 **배율만큼 곱하지 않는다.** 논리 좌표계를 보존하는 것이 이 설계의 핵심이다. (참고 프로젝트는 좌표계 자체를 배율만큼 키웠지만, 그건 처음부터 그렇게 설계했기 때문에 가능했다. 이 저장소는 8개 스테이지에 좌표가 하드코딩돼 있어 같은 방식을 쓰면 수치 하나만 빠뜨려도 게임 밸런스가 조용히 깨진다.)
- 세로 논리 크기를 540에서 바꾸지 않는다. 검은 띠를 없애려고 세로를 늘리지 말고, **가로만** 조절한다.
- HUD를 위해 별도 씬이나 별도 카메라를 새로 만들지 않는다. 카메라가 보는 영역 기준 배치로 충분하다.
- 히트박스를 "고치지" 않는다. 지금 값이 이상해 보여도 그대로 유지한다. 이 작업의 목표는 선명도이고, 히트박스는 **변하지 않아야 하는 것**이다.
- 이 작업과 무관한 코드를 정리하거나 리팩터링하지 않는다.

## 고려사항

**가로 시야가 창에 따라 달라진다.** 세로를 540으로 고정하고 띠를 없애면 논리 가로가 창 비율을 따라간다. 창이 16:9보다 세로로 길면 960보다 좁게(예: 907), 가로로 길면 960보다 넓게 보인다. 스테이지가 전부 가로로 길고(2400~5200) 카메라가 플레이어를 따라가므로 진행에는 문제가 없다.

**다만 아주 넓은 창에서는 연출이 깨진다.** 발사체는 900 논리 단위를 날아가면 사라진다. 논리 가로가 1280이 되는 초광각 창(2560×1080 등)에서는 7스테이지 화살 관문의 소멸 지점(x=2170)이 화면 안에 들어와, 화살이 공중에서 사라지는 것이 보인다. 그래서 논리 가로 상한을 1100으로 두고, 그보다 넓은 창에서만 좌우에 얇은 띠를 만든다. 하한 854는 그 반대쪽(세로로 매우 긴 창)에서 시야가 지나치게 좁아지는 것을 막는다.

**버퍼가 커지면 그리기 비용이 늘어난다.** 960×540 → 3024×1800은 픽셀 수가 10배다. 이 게임은 도형 몇십 개만 그리므로 문제되지 않을 것으로 보지만, 화면 배율 인정 상한을 3으로 두어 최악의 경우를 제한한다. 프레임이 떨어지면 상한을 낮추는 것이 첫 번째 대응이다.

**최근접 이웃 확대를 끄면 "정수 배율" 규칙이 무의미해진다.** 지금 켜져 있는 픽셀 정렬은 카메라 배율이 정수일 때만 실제로 동작한다(소스 확인). 배율이 3.333 같은 값이 되면 어차피 동작하지 않으므로, 매끄러운 확대로 가는 것과 모순되지 않는다.

**창 크기 변화 중 계산이 요동칠 수 있다.** 드래그로 창을 줄이는 동안 매 이벤트마다 버퍼를 다시 만들면 비용이 크다. Phaser가 이미 일정 간격으로만 크기를 확인하므로 그 주기에 맞춰 처리한다.

## 제약사항

- Phaser 4.2.1에 화면 배율 대응 기능이 없다. 전부 직접 구현해야 한다.
- 브라우저 API(`window.devicePixelRatio`, `window.innerWidth`)에 의존하므로, 계산 로직은 반드시 순수 함수로 분리해서 테스트한다(이 저장소 `pure-logic-testing` 규칙).
- 기존 테스트는 순수 로직만 다루고 렌더링을 다루지 않는다. 따라서 화면 관련 검증은 실제 브라우저 확인으로 대체한다.
- 스프라이트 그림은 파일이 아니라 부팅 시 코드로 그려진다. 그래서 2단계의 텍스처 확대는 그림 파일 교체 없이 가능하다.

## 작업 순서

각 항목은 완료조건을 만족했는지 확인한 뒤 다음으로 넘어간다.

1. **화면 계산 순수 함수 + 테스트** — 완료조건: 정상·경계·예외 3종 테스트 통과. 경계는 제한에 걸리는 창, 화면 배율 1인 창, 상한을 넘는 화면 배율.
2. **게임 설정과 문서 페이지 전환** — 완료조건: 캔버스 버퍼가 물리 픽셀과 일치, 콘솔 오류 없음.
3. **카메라 배율과 창 크기 변화 처리** — 완료조건: 카메라가 보는 세로가 540, 창을 바꿔도 유지.
4. **플레이 화면 HUD 재배치** — 완료조건: 4개 표시물이 화면 안쪽 제자리, 글자 선명.
5. **제목·게임오버·클리어 화면 정렬** — 완료조건: 중앙 정렬 유지, 글자 선명.
6. **실제 브라우저 검증** — 완료조건: 위 완료조건 1~8 전부 확인, 이동·점프·낙사 동작 확인.
7. **(분리) 텍스처 선명화와 몸체 크기 보정** — 완료조건: 몸체 크기 불변 테스트 통과 + 브라우저에서 히트박스 확인. 실패 시 이 단계만 되돌린다.
