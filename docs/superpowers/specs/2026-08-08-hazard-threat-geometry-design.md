# 해저드 위협 기하 교정 설계 — "가만히 서 있으면 안 죽는" 문제

작성일: 2026-08-08

## 1. 개요 (무엇을 / 왜)

플레이 중 여러 해저드가 **주인공을 위협하지 못하는** 상태다. 스나이퍼(터렛)는 공중에 떠서 발사선이 머리 위로 지나가고, 톱니바퀴는 왕복 범위가 좁아 발판에 서 있는 주인공에게 닿지 않으며, 깃발은 지면보다 64px 위에 떠 있어 점프해야만 스테이지가 끝난다.

이 작업은 8개 스테이지 전체를 실측해 **"가만히 서 있는 주인공을 죽일 수 있는가"를 기준으로 모든 해저드를 교정**하고, 같은 문제가 다음 스테이지에서 재발하지 않도록 자동 검사와 규칙 문서를 남긴다.

범위 밖: 새 해저드 종류 추가, 아트 변경, 사운드, 스테이지 구조 재설계.

## 2. 판정 기준

| 용어 | 정의 | 지면(윗면 y=496) 기준 값 |
|---|---|---|
| **표면** | 발판의 윗면 y좌표. 레벨 데이터의 발판은 왼쪽 위 모서리 + 크기로 정의되므로 `platform.y`가 곧 표면이다 | 496 |
| **서있는 몸통 밴드** | 주인공이 표면에 가만히 서 있을 때 히트박스가 차지하는 세로 구간. 히트박스는 24×38 논리단위 (`src/objects/Player.ts:48`) | 458 ~ 496 |
| **위험 밴드** | 해저드의 히트박스가 지나가는 세로 구간(움직이는 것은 전체 이동 범위) | 항목별 |

**두 밴드가 겹치지 않으면 서 있는 주인공은 그 해저드로 절대 죽지 않는다.** 이 문서의 모든 판정은 이 한 문장에서 나온다.

교정 목표치는 **겹침 8px 이상**으로 잡는다. 2px짜리 스침은 맞았는데 빗나간 것처럼 보이고, 반대로 너무 깊게 넣으면 통과할 시간 창이 사라지기 때문이다.

## 4. 근본 원인 3가지

### 원인 1 — 터렛 배치 코드가 텍스처 크기를 논리 크기로 착각

`src/objects/Turret.ts:59`:

```ts
this.setPosition(x, y - this.height / 2);   // this.height = 텍스처 픽셀
```

텍스처는 논리 크기의 `TEXTURE_SCALE`배로 생성되고 스프라이트는 그만큼 축소된다(`src/display.ts`). 따라서 논리 높이는 `displayHeight`(30)이고 `height`는 텍스처 높이(30 × TEXTURE_SCALE)다. 이 자리에 텍스처 높이가 들어가 있어, **화면 픽셀비에 따라 뜨는 높이가 달라진다**:

| 디스플레이 | TEXTURE_SCALE | 표면에서 뜨는 높이 |
|---|---|---|
| 일반 (픽셀비 1) | 2 | 15px |
| 레티나 (픽셀비 2) | 4 | **45px** |

같은 레벨 데이터가 기기마다 다르게 동작하므로, 좌표를 아무리 조정해도 근본 해결이 안 된다.

### 원인 2 — 같은 "바닥 설치물"인데 y의 의미가 셋 다 다름

| 오브젝트 | 레벨 데이터 y의 의미 | 결과 |
|---|---|---|
| 터렛 | 딛고 선 표면 (의도) | 위 계산 버그로 공중 |
| 대포 · 화살 발사기 | 스프라이트 중심 | 저자가 감으로 452를 찍음 → 탄도가 머리 위 |
| 깃발 | 밑동 | 저자가 "윗변"으로 오해 → 정확히 깃발 높이(64)만큼 공중 |

### 원인 3 — 위협 여부를 확인할 방법이 없음

화살이 머리 위 1px로 지나가는 것은 플레이로 알아챌 수 없다. "안 맞았다"로만 느껴지기 때문이다. 좌표를 눈으로 찍고 확인하지 않는 이상 조용히 들어오는 종류의 결함이다.

## 5. 설계 1 — 좌표 규약을 "딛고 선 바닥선"으로 통일

**바닥에 서는 모든 설치물의 레벨 데이터 `y`는 딛고 선 표면**으로 통일한다. 발판 정의가 이미 표면 좌표(`{ x, y: 496, ... }`)이므로, 대포도 `y: 496`을 적게 되어 데이터를 읽는 것만으로 어디 놓였는지 알 수 있다.

이 규약의 부수 효과가 핵심이다. 표면 S에 세운 설치물의 발사 높이는 자동으로 다음이 되고, 이는 **별도 튜닝 없이 서있는 몸통 밴드 `[S-38, S]` 안에 들어온다**:

| 설치물 | 스프라이트 중심 | 발사체 밴드 | 지면(496)일 때 |
|---|---|---|---|
| 대포 (40×30, 포탄 지름 16) | S − 15 | [S−23, S−7] | 473~489 |
| 화살 발사기 (26×34, 화살 22×10) | S − 17 | [S−22, S−12] | 474~484 |
| 터렛 (34×30, 총구는 스프라이트 윗변) | S − 15 | [S−35, S−25] | 461~471 |

### 공용 배치 함수 (신규 `src/objects/mount.ts`)

```ts
/** 스프라이트의 밑동이 surfaceY에 닿도록 세운다. */
export function standOnSurface(sprite, x, surfaceY): void
```

Phaser를 import하지 않고 필요한 속성만 구조적 타입으로 받는다 — 기존 `src/objects/hitbox.ts`와 같은 방식이라 `mount.test.ts`로 단위테스트할 수 있다.

| 파일 | 변경 |
|---|---|
| `src/objects/Turret.ts` | `y - this.height / 2` → `standOnSurface(this, x, y)` |
| `src/objects/Cannon.ts` | 생성자에서 `standOnSurface(this, def.x, def.y)` |
| `src/objects/Shooter.ts` | 정적 바디 생성 **전에** `standOnSurface` 호출 (정적 바디는 배치 후 옮기면 `updateFromGameObject()`가 필요하므로 순서를 지킨다) |

`this.height`(텍스처)와 `this.displayHeight`(논리)를 헷갈리는 실수가 세 곳으로 흩어지지 않고 한 곳에만 존재하게 된다 — 이번 버그의 재발을 구조적으로 막는 유일한 방법이다.

## 6. 설계 2 — 판정에 쓰이는 수치를 config로 중앙화

지금 히트박스·스프라이트 크기가 코드 여러 곳에 흩어져 있다. 검사 코드가 이 숫자들을 따로 들고 있으면 "테스트는 통과하는데 실제로는 안 맞는" 상태가 생기므로, `src/config.ts` 한 곳에서 공유한다. 레포 규칙(`.claude/rules/no-hardcoded-tuning.md`)과도 일치한다.

| 추가할 상수 | 값 | 지금 어디에 있나 |
|---|---|---|
| `PLAYER.BODY_WIDTH` / `BODY_HEIGHT` | 24 / 38 | `Player.ts:48`에 하드코딩 |
| `PROJECTILE.WIDTH` / `HEIGHT` | 22 / 10 | `BootScene.ts` 텍스처 생성부 |
| `SHOOTER.WIDTH` / `HEIGHT` | 26 / 34 | 〃 |
| `TURRET.WIDTH` / `HEIGHT` | 34 / 30 | 〃 |
| `CANNON.WIDTH` / `HEIGHT` / `BALL_DIAMETER` | 40 / 30 / 16 | 〃 |
| `SPIKE.BODY_WIDTH` / `BODY_HEIGHT` / `BODY_OFFSET_X` / `BODY_OFFSET_Y` | 28 / 18 / 2 / 14 | `GameScene.buildSpikes`와 `PopupSpike.ts`에 **중복** 하드코딩 |

톱니 반지름(`GEAR.RADIUS`), 진자 머리 반지름(`PENDULUM.HEAD_RADIUS`), 타일 크기(`TILE`)는 이미 config에 있어 그대로 쓴다.

`BootScene`의 해당 텍스처 생성부는 이 상수를 읽도록 바꾼다(그림 자체는 변하지 않는다).

## 7. 설계 3 — 자동 검사

### 검사할 두 규칙

| 규칙 | 내용 | 잡아내는 것 |
|---|---|---|
| **설치 검증** | 바닥 설치물(터렛·대포·화살 발사기·팝업 가시)**과 깃발**의 `y`는 그 x 위치에 실제로 존재하는 발판 윗면과 일치해야 한다 | 공중에 뜬 설치물, 공중에 뜬 깃발 |
| **위협 검증** | 해저드의 위험 밴드가, 그 위험이 걸치는 x 범위 안 **어떤 표면의** 서있는 몸통 밴드와 겹쳐야 한다 | 아무도 못 맞히는 해저드 |

조준형 터렛은 주인공 위치를 조준하므로 위협 검증에서 제외하고 설치 검증만 적용한다.

### 모듈 (신규 `src/levels/threat.ts`)

Phaser 의존 없는 순수 기하 함수 — 레포 규칙(`.claude/rules/pure-logic-testing.md`)의 기존 패턴(`motion.ts`, `patrol.ts`, `ballistics.ts`)을 따른다.

```ts
type Band = { top: number; bottom: number };

standingBand(surfaceY)          // 서 있는 몸통 세로 구간
bandsOverlap(a, b)              // 두 구간이 겹치는가
surfaceSpans(platforms)         // 표면 목록 {top, left, right}
                                //   이동 발판은 왕복 범위만큼 확장 (타고 있는 주인공도 표면 위에 있다)
hazardThreat(hazard)            // 해저드의 위험 밴드 + 걸치는 x 범위
                                //   진자: 호의 최저점까지 / 톱니: 레일 끝까지
                                //   발사체: 총구에서 지형에 막히는 지점까지
mountedSurfaceOf(level, hazard) // 설치 검증용 — 그 자리에 발판이 있는가
threatensStandingPlayer(level, hazard)
```

### 테스트 (신규 `src/levels/threat.test.ts`)

레포 규칙에 따라 세 카테고리를 모두 포함한다.

| 카테고리 | 예 |
|---|---|
| 정상 | 지면 대포의 포탄 밴드가 서있는 몸통과 겹친다 |
| 경계 | 1px만 겹칠 때 / 딱 맞닿아 안 겹칠 때 / 이동 발판이 왕복 끝에 있을 때 / 진자 진폭 0 |
| 오류 | 알 수 없는 해저드 종류, 발판이 없는 x에 설치, 왕복 범위 0인 톱니 |

여기에 **8개 스테이지 전수 검사**를 더한다. `levels` 배열을 순회하며 모든 해저드에 두 규칙을 적용하고, 실패 시 사람이 읽을 수 있게 보고한다:

```
3스테이지 진자(x=1260): 머리 최저점 436, 필요 458 — 22px 모자람
```

**탄도가 지형으로 끝맺는지는 자동 검사에 넣지 않는다.** 사정거리 제한은 스테이지마다 의도가 달라(뒤쪽으로 날아가는 탄은 무해하다) 기계 판정이 오히려 방해가 된다. 대신 규칙 문서에 남겨 사람이 리뷰에서 확인한다.

## 8. 설계 4 — 규칙 문서

신규 `.claude/rules/hazard-must-threaten.md` (기존 규칙 파일 두 개와 같은 자리, 자동 로드됨). 담을 내용:

1. 해저드를 놓거나 고칠 때 **"서 있는 주인공을 맞힐 수 있는가"를 계산으로 확인**한다. 서있는 몸통 구간 = `[표면 − PLAYER.BODY_HEIGHT, 표면]`.
2. 바닥 설치물의 레벨 데이터 `y`는 **딛고 선 표면**이며, 배치는 `standOnSurface()`로 한다. `height`(텍스처 픽셀)와 `displayHeight`(논리 픽셀)를 혼동하면 화면 픽셀비에 따라 다르게 뜨는 버그가 난다.
3. 판정에 쓰이는 크기는 `config.ts`에 두어 게임과 검사가 같은 값을 본다.
4. 새 해저드 종류를 추가하면 `threat.ts`의 위험 밴드 계산에도 등록하고 전수 검사를 통과시킨다.
5. 가로로 긴 탄도는 지형으로 끝맺는다. 특히 **주인공 진행 방향(오른쪽)으로 날아가는 탄**은 도착 전에 발사된 것이 예고 없이 날아오므로 반드시 막는다.

`CLAUDE.md`의 "게임 로직 관례"에는 이 규칙을 가리키는 한 줄만 추가한다.

## 9. 레벨별 변경 목록

### 9.1 깃발 — 8개 스테이지 전부

`goal.y: 432 → 496`. 판정 영역이 432~496이 되어 서있는 몸통(458~496)과 겹치므로 **걸어가기만 해도 클리어**된다.

### 9.2 스나이퍼 (터렛)

| 스테이지 | 변경 | 결과 |
|---|---|---|
| 5 · 고정형 | `(600, 400)` → `(600, 496)` | 선반에서 지면으로 내려온다. 발사선 461~471이 서있는 몸통 안에 완전히 들어간다. **바로 위 선반(520~680, 윗면 400)이 그대로 밟기용 발판**이 되어 "위에서 밟아 처치"는 유지된다 |
| 5 · 조준형 2기<br>7 · 조준형 1기 | 데이터 변경 없음 | 이미 표면 규약대로 `y=496`이라 코드 수정만으로 지면에 앉는다 |

지면으로 내려온 고정형 터렛은 옆에 닿으면 죽으므로, 밟거나 뛰어넘어야 하는 실제 장애물이 된다.

| 스테이지 | 변경 | 화살 높이 | 탄도 종결 |

| 7 (x=3070) | `y: 452 → 496` | 〃 | 엄폐 기둥(2700~2740)까지 330px |

| 7 (x=5180) | `y: 452 → 496` | 473~489 | 벽(4860~4900)까지 280px |
| 8 (x=4960) | `y: 452 → 496` | 473~489 | 기존 저지 기둥(4000)까지 960px |

**6스테이지에 저지 기둥이 필요한 이유**: 포탄을 가슴 높이로 내리면 왼쪽 2360px 전체가 사정권이 된다. 주인공이 도착하기 한참 전에 발사된 포탄이 예고 없이 날아오는 상태가 되므로, 8스테이지가 이미 쓰고 있는 저지 기둥 방식으로 사정거리를 300px로 가둔다. 기둥은 44px 높이라 넘어가는 데 부담이 없다.

**7스테이지 대포만 받침대를 세우는 이유**: 이 대포의 임무는 *이동 발판을 타고 구덩이를 건너는 주인공*을 노리는 것이다. 탑승자의 몸통 밴드는 414~452이므로 지면(496)에 세우면 포탄이 발밑으로 지나가 지금보다 못해진다. 이동 발판 탑승 높이(452)에 받침대를 세워 그 위에 올리면 포탄 429~445가 탑승자 몸통 한가운데를 지난다. 받침대는 지면 위에 얹히므로(452~496) 시각적으로도 포대가 된다.

### 9.5 하늘 대포 2문 — 정상 발판 위를 쓸도록 이동

포탄이 지나는 높이에 발판이 없어 아무도 못 맞히는 상태다. 대포를 **정상 발판의 반대쪽 끝으로 옮겨, 왼쪽으로 쏘는 탄이 정상 발판 위를 훑도록** 만든다.

| 스테이지 | 변경 | 결과 |
|---|---|---|
| 6 정상 | `(1270, 205)` → `(1340, 220)` | 포탄 197~213이 정상 발판(1260~1360, 윗면 220) 위 몸통 182~220을 관통 |
| 8 1구역 | `(1060, 245)` → `(1140, 260)` | 포탄 237~253이 정상 발판(1050~1160, 윗면 260) 위 몸통 222~260을 관통 |

발사 방향은 **왼쪽 그대로** 둔다. 오른쪽으로 쏘면 주인공이 도착하기 전에 발사된 탄이 예고 없이 날아오지만, 왼쪽은 이미 지나온 구역이라 그 문제가 없다.

6스테이지는 이 변경으로 **바로 앞(1120)의 방패 아이템이 비로소 쓸모를 갖는다** — 지금은 정상 대포가 아무도 못 맞혀서 방패가 무용지물이다.

### 9.6 진자 3개 — 줄이 아니라 매다는 지점을 내림

| 위치 | 피벗 y | 머리 최저점 | 몸통 침범 |
|---|---|---|---|
| 3스테이지 x=1260 (줄 170) | 250 → **280** | 436 → 466 | 8px |
| 7스테이지 x=1520 (줄 180) | 250 → **270** | 446 → 466 | 8px |
| 7스테이지 x=1700 (줄 150) | 260 → **300** | 426 → 466 | 8px |

**줄을 늘리지 않는 이유**: 줄이 길어지면 좌우 스윙 폭도 함께 넓어져(호의 반지름이 커지므로) 통로 전체가 위험 구간이 되고, 원래 설계된 통과 창이 사라진다. 피벗만 내리면 스윙 폭과 주기는 그대로 두고 높이만 교정된다.

### 9.7 톱니바퀴

| 위치 | 변경 | 결과 |
|---|---|---|
| 8스테이지 수평 (x=1860) | 시작점 `1860 → 1790`, 왕복 `100 → 170` | 왕복 구간(반지름 포함 1770~1980)이 방패 발판(1760~1860) 전체를 덮어, 그 발판 **어디에 서 있어도** 톱니가 지나간다 |
| 8스테이지 수직 2기 | 변경 없음 | 최저점 490 / 470으로 이미 서있는 몸통을 침범 |

수평 톱니는 밑면(320)이 발판 윗면(320)과 같아 발판 위를 굴러가는 것처럼 보인다. 방패를 먹으려면 톱니가 오른쪽 끝에 가 있을 때를 노려야 한다.

### 9.8 손대지 않는 것

팝업 가시 · 스톰프 바위 · 적 · 고정 가시는 이미 서있는 몸통을 정확히 침범하고 있어 그대로 둔다(검사에는 포함해 회귀를 막는다).

## 10. 통과 가능성 검증

교정으로 통과가 불가능해지면 안 되므로, 위험 구간을 지나는 데 걸리는 시간과 안전 창을 계산했다. 이동 속도는 260px/s(`PLAYER.MOVE_SPEED`)다.

### 진자

위험한 순간은 머리가 낮게 내려온 때뿐이고, 진자는 사인파로 움직여 양 끝에서 느려지고 중앙에서 가장 빠르다. 따라서 "머리가 몸통 높이까지 내려와 있는" 시간은 반주기 중 일부다.

| 구간 | 위험 x 폭 | 통과 소요 | 반주기당 안전 시간 | 판정 |
|---|---|---|---|---|
| 3스테이지 (주기 2100ms) | 135px (1193~1328) | 0.52초 | 0.84초 | ✅ |
| 7스테이지 첫 진자 (주기 2000ms) | 138px (1451~1589) | 0.53초 | 0.82초 | ✅ |
| 7스테이지 둘째 진자 (주기 1700ms) | 129px (1636~1764) | 0.50초 | 0.64초 | ✅ |

7스테이지는 진자가 2개지만 두 위험 구간 사이에 **47px의 안전 지대(1589~1636)**가 남는다. 주인공 폭이 24px이므로 한 번에 통과하지 않고 중간에서 끊어 갈 수 있다.

### 하늘 대포 (6스테이지 정상)

주인공은 아래 발판(1080~1180, 윗면 270)에서 대기할 수 있고 포탄은 그 머리 위 19px로 지나간다. 거기서 발사 리듬을 읽고 정상 발판으로 올라가 100px을 질주하면 된다.

| 항목 | 값 |
|---|---|
| 정상 발판 횡단 거리 | 100px → 0.38초 |
| 발사 간격 | 1.5초 |
| 안전 창 | 약 1.3초 |

### 지상 대포 · 화살 발사기

엄폐물 뒤에서 기다렸다 지나가는 기존 설계 그대로이며, 탄도 길이만 300~960px로 지형에 의해 끝맺는다.

## 13. 별도로 발견한 사항 (이번 범위 밖, 보고만 함)

- `POPUP_SPIKE.RISE`(값 26)는 `src/config.ts`에 정의만 되어 있고 어디서도 쓰이지 않는다. `PopupSpike.ts`는 대신 `TILE / 2`로 솟는 높이를 계산한다.
- `src/display.ts`의 `LOGICAL_WIDTH_MAX` 주석은 7스테이지 화살이 x=2170까지 날아간다고 설명하지만, 실제로는 그 앞의 엄폐 기둥(2700~2740)에 막혀 그만큼 날아가지 못한다. 이번 변경으로도 여전히 막히므로 동작에는 영향이 없다.
