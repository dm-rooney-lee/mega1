# 타이틀·사망·클리어 화면에 그림 넣기

작성일: 2026-08-08

## 1. 개요 (무엇을 / 왜)

지금 게임을 하지 않는 세 화면 — 타이틀, 죽음, 전체 클리어 — 은 **글자만 있다.** 가운데 정렬된 문장 서너 줄이 전부고, 배경은 게임 전체에 깔린 남색 한 가지다. 게임 안은 고퍼·발판·가시가 그려져 있는데 화면 밖으로 나오면 갑자기 밋밋해진다.

이번 작업은 시안 그림을 바탕으로 세 화면에 **배경색과 그림을 넣고, 글꼴을 픽셀 서체로 바꾼다.** 게임 제목도 `PLATFORMER POC`에서 `Let's go!!`로 바꾼다.

**게임 규칙·물리·난이도·소리는 일절 건드리지 않는다.** 스테이지 안에서 벌어지는 일은 그대로다. 바뀌는 것은 플레이와 플레이 사이에 보이는 세 장면의 겉모습뿐이다.

## 2. 화면이 쌓이는 방식

세 화면 모두 같은 3층 구조로 만든다.

```
┌──────────────────────────────────────────────┐
│ 3층  글자 — 코드가 그린다 (픽셀 서체)          │  값이 변하는 문구 포함
│ 2층  그림 — SVG 파일 1장, 화면 가운데 고정     │  시안의 일러스트
│ 1층  배경색 — 코드가 화면 전체를 칠한다        │  잘림도 빈틈도 없다
└──────────────────────────────────────────────┘
```

배경색을 그림 파일에 넣지 않는 것이 이 구조의 핵심이다. 게임 화면은 세로 540으로 고정이지만 **가로가 854~1100 사이에서 창 비율을 따라 변한다**(`src/display.ts`). 배경까지 그림 한 장에 담으면 넓은 창에서는 좌우가 잘리고 좁은 창에서는 다르게 잘려, 그림마다 안전 범위를 따로 계산해야 한다. 배경을 코드가 칠하면 어떤 비율에서도 화면이 꽉 찬다.

배경 칠하기는 화면마다 한 줄이면 된다.

```ts
this.cameras.main.setBackgroundColor(COLORS.TITLE_SKY);
```

## 3. 화면별 구성

좌표와 크기는 모두 **논리 단위**(세로 540 기준)다. `y`는 글자·그림의 세로 중심이다.

### 타이틀 (`MenuScene`)

```
        배경 전체: 하늘 파랑
  y=150   Let's go!!                    크기 64 · 하늘색 채움 + 진파랑 외곽선
  y=210 ┌────────────────────────────┐
        │  지형 띠 그림 (1100 × 180)  │  발판 · 고퍼 · 빨간 적 · 가시
  y=390 └────────────────────────────┘
  y=445   press any key to start        크기 18 · 깜빡임
```

- 지금의 부제 `a tiny Phaser 4 platformer`는 **없앤다.** 시안 타이틀에 부제가 없고, 한 줄 제목 + 안내문 구성이 더 깔끔하다.
- 시작 안내문의 깜빡임(현재 있는 연출)은 그대로 둔다.

### 죽음 (`GameOverScene`)

```
        배경 위쪽: 어두운 자주 / 아래쪽(y=245 아래): 밝은 자주
  y=130   YOU DIED                      크기 80 · 빨강 + 검정 외곽선  (아래끝 170)
  y=210   [그림 400 × 70]  적 + 흰 가시 4개  (위끝 175 · 아래끝 245)
  y=245 ────────────────────────────    밝은 마젠타 가로선 (화면 폭 전체)
  y=340   GAME OVER                     크기 30 · 살구빛
  y=385   STAGE N/8                     크기 20 · 죽은 스테이지 번호
  y=455   press SPACE / ENTER or TAP to retry    크기 16
  y=495   ESC for menu                  크기 14
```

- 위아래 두 가지 자주색과 그 경계의 가로선은 **코드가 화면 폭 전체에 그린다.** 창이 넓어져도 선이 끊기지 않아야 하기 때문이다. 그림 파일에는 적과 가시만 담는다.
- `STAGE 7/8`이 새로 생기는 줄이다. 죽은 스테이지 번호는 이미 이 화면으로 전달되고 있다.

### 전체 클리어 (`WinScene`)

```
        배경 전체: 진초록
  y=120   YOU WIN!                      크기 76 · 연두 + 진초록 외곽선
  y=270   [그림 420 × 180]  월계관 쓴 고퍼 + 반짝임
  y=390   CONGRATULATIONS!              크기 28
  y=425   all stages cleared            크기 18
  y=475   press SPACE / ENTER or TAP to play again   크기 14
  y=510   ESC for menu                  크기 14
```

- 시안에 있는 `final score: 9999`는 **넣지 않는다.** 이 게임에는 점수 개념 자체가 없다.

## 5. 그림 파일

기존 배경음악과 같은 방식으로 `public/` 아래에 두고 주소로 불러온다.

| 파일 | 크기 (논리) | 담기는 것 |
|---|---|---|
| `public/ui/title-scene.svg` | 1100 × 180 | 잔디 발판 3~4개, 오른쪽에 뜬 발판, 고퍼, 빨간 적, 가시 |
| `public/ui/death-scene.svg` | 400 × 70 | 빨간 적, 흰 가시 4개 |
| `public/ui/win-gopher.svg` | 420 × 180 | 월계관 쓴 고퍼, 반짝임 |

### 만드는 방법

시안 PNG를 자동 벡터 변환 도구에 넣지 **않는다.** 시안에는 아이패드·아이폰 테두리와 `Web/mobile screen` 같은 설명 글자가 함께 들어 있어 통째로 변환할 수 없고, 원본이 블록형 픽셀 그림이라 **사각형·삼각형을 나열해 새로 작성**하는 편이 훨씬 깨끗하다. 게임 안의 그림(`BootScene`)을 그리는 방식과 같은 발상이다.

### 배경을 투명하게 둔다

그림 파일에는 배경을 칠하지 않는다. 배경은 2절대로 코드가 담당한다.

### 파일에 크기를 반드시 적는다

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="1100" height="180" viewBox="0 0 1100 180">
```

Phaser는 이 `width`/`height` 값을 읽어서 크기를 바꾼 뒤 그림으로 굽는다. 없으면 크기 조정이 동작하지 않는다(7절 참고).

### 얼마나 크게 굽는가

게임의 나머지 그림과 같은 규칙(`TEXTURE_SCALE`, `src/display.ts`)을 쓴다. 화면 배율이 2인 기기에서는 4배로 구워진다.

| 파일 | 구워진 크기 | 메모리 |
|---|---|---|
| `title-scene.svg` | 4400 × 720 | 약 12.7MB |
| `death-scene.svg` | 1600 × 280 | 약 1.8MB |
| `win-gopher.svg` | 1680 × 720 | 약 4.8MB |

합쳐서 약 19MB. 화면 배율이 3인 기기에서는 6배로 구워져 약 43MB가 된다. 감당 못 할 양은 아니지만, 나중에 문제가 되면 굽는 배율에 상한을 거는 것으로 조절할 수 있다.

### 좁은 화면에서 잘리는 것

타이틀 지형 띠만 가로 1100이라 **가장 좁은 화면(가로 854)에서는 좌우가 123씩 잘린다.** 그래서 고퍼·적·가시는 **가운데 854 폭 안**에 배치하고, 잘려도 되는 것(양 끝 발판)만 바깥에 둔다. 죽음·클리어 화면의 그림은 400~420 폭이라 어떤 화면에서도 잘리지 않는다.

## 6. 글꼴

### 무엇을

**Press Start 2P** — 시안의 블록형 서체와 가장 가깝고, 자유 사용 라이선스(SIL Open Font License)라 게임에 포함해 배포할 수 있다. 실제 파일과 라이선스 전문은 구현 시점에 내려받아 확인하고, 라이선스 파일과 함께 `public/fonts/`에 둔다.

### 어떻게 불러오는가

`index.html`에 글꼴을 선언하고, `src/main.ts`가 **글꼴을 다 받은 뒤에 게임을 시작한다.**

```ts
await document.fonts.load('16px "Press Start 2P"').catch(() => {});
new Phaser.Game(config);
```

기다리지 않으면 첫 화면이 한순간 기본 글꼴로 그려졌다가 바뀐다. Phaser가 글자를 그림으로 구워 쓰기 때문에, 나중에 글꼴이 도착해도 이미 그려진 글자는 저절로 바뀌지 않는다.

### 못 받았을 때

글꼴 목록을 `"Press Start 2P", monospace`로 적어두면 파일을 못 받아도 지금 쓰는 고정폭 글꼴로 그려진다. 게임은 정상 동작한다. 위의 `.catch(() => {})`는 파일이 아예 없을 때(주소 오타, 배포 누락) 게임이 시작조차 못 하는 것을 막는다.

### 글자가 넓어진다

이 글꼴은 글자 하나가 정사각형이라 지금 글꼴보다 훨씬 넓게 퍼진다. 3절의 글자 크기는 **글자 하나가 대략 글자 크기만큼의 가로폭을 차지한다**고 보고 잡은 값이다.

| 문구 | 글자 수 | 크기 | 예상 가로폭 | 가장 좁은 화면(854)에서 |
|---|---|---|---|---|
| `Let's go!!` | 10 | 64 | 640 | 여유 107씩 |
| `YOU DIED` | 8 | 80 | 640 | 여유 107씩 |
| `YOU WIN!` | 8 | 76 | 608 | 여유 123씩 |
| `press SPACE / ENTER or TAP to play again` | 40 | 14 | 560 | 여유 147씩 |

글꼴을 받은 뒤 실제 폭을 재서 크기를 확정한다. 넘치면 크기를 낮추거나 문구를 두 줄로 나눈다.

## 7. 검증한 Phaser 동작 (추측 아님)

설치된 **Phaser 4.2.1**의 소스와 타입 정의를 직접 확인했다.

- `this.load.svg(key, url, svgConfig)`가 존재한다. `svgConfig`는 `{ width, height }` 또는 `{ scale }`을 받는다. 셋 다 주면 `scale`이 이긴다.
- **SVG는 벡터로 유지되지 않는다.** 불러오는 시점에 지정한 크기로 한 번 그림(픽셀)으로 구워서 텍스처로 쓴다. 창을 키워도 다시 굽지 않는다 — 그래서 5절처럼 "얼마나 크게 굽는가"를 미리 정해야 한다.
- 크기 조정은 파일 루트의 `width`/`height` 속성을 읽어서 계산한다(`SVGFile.js`). 속성이 없으면 조정이 동작하지 않는다.

## 8. 손대는 파일

| 파일 | 무엇을 |
|---|---|
| `src/scenes/textScreen.ts` → `src/scenes/screen.ts` | **그림도 배치할 수 있게 확장.** 지금은 글자 줄만 등록해두고 창 크기가 바뀔 때 다시 배치하는데, 그림에도 똑같은 규칙이 필요하다. 글자 전용이 아니게 되므로 함수 이름을 `centredTextScreen` → `centredScreen`으로, 파일 이름을 `screen.ts`로 바꾼다. 부르는 곳은 세 군데뿐이다. |
| `src/scenes/BootScene.ts` | `preload()`에 그림 3장 불러오기 추가 (배경음악을 불러오는 바로 그 자리) |
| `src/scenes/MenuScene.ts` | 배경색, 지형 띠 그림, `Let's go!!` 제목. 부제 제거 |
| `src/scenes/GameOverScene.ts` | 배경색 두 가지 + 경계선, 적·가시 그림, `GAME OVER` + `STAGE N/8` 줄 |
| `src/scenes/WinScene.ts` | 배경색, 월계관 고퍼 그림, `CONGRATULATIONS!` 줄 |
| `src/config.ts` | 4절의 색을 `COLORS`에, 그림 이름 3개를 `TEX`에 추가 |
| `index.html` | 글꼴 선언 |
| `src/main.ts` | 글꼴을 받은 뒤 게임 시작 |
| `public/ui/*.svg` (신규 3개) | 그림 |
| `public/fonts/*` (신규) | 글꼴 파일 + 라이선스 |
| `README.md` | 직접 확인 항목에 세 화면 점검 추가 |

### 화면 도우미가 그림을 다루는 방식

글자와 **똑같은 규칙**을 쓴다. 논리 좌표로 등록해두고, 화면 배율이 바뀔 때마다 `배율 × 논리값`으로 위치와 크기를 다시 잡는다. 새 개념이 하나도 들어가지 않는다.

```ts
// 글자: 이미 이렇게 하고 있다
row.text.setFontSize(Math.round(row.size * scale)).setPosition(cx, row.y * scale);

// 그림: 같은 규칙
row.image.setDisplaySize(row.w * scale, row.h * scale).setPosition(cx, row.y * scale);
```

## 9. 뭔가 잘못됐을 때

| 상황 | 결과 |
|---|---|
| 그림 파일을 못 받음 | 그림이 있는지 확인한 뒤에만 배치하므로 **배경색과 글자는 정상 표시**된다. Phaser 기본 동작인 초록 물음표 상자가 뜨지 않는다. |
| 글꼴 파일을 못 받음 | 지금 쓰는 고정폭 글꼴로 자동 대체된다. 게임은 그대로 동작한다. |
| 개발용 `?stage=7`로 타이틀을 건너뜀 | 지금과 동일하게 타이틀을 거치지 않고 바로 진입한다. 그림은 `BootScene`에서 이미 다 받아둔 뒤라 영향 없다. |
| 죽은 스테이지 번호가 범위 밖 | 가장 가까운 유효 번호로 보정한다. 지금 이 화면이 `?? 0`으로 방어하는 태도와 같다. |

## 10. 완료조건

### 자동 검증

```bash
npm test        # 스테이지 표기 문구 테스트가 통과할 것
npm run build   # 타입 검사 + 빌드가 통과할 것
```

이번에 새로 생기는, Phaser 없이 돌아가는 순수 로직은 **스테이지 표기 문구를 만드는 함수** 하나다. 여기에 테스트를 붙인다.

- `[정상]` 7번째 스테이지에서 죽음 → `STAGE 7/8`
- `[경계]` 첫 스테이지 → `STAGE 1/8`
- `[경계]` 마지막 스테이지 → `STAGE 8/8`
- `[오류]` 음수 번호 → `STAGE 1/8`로 보정
- `[오류]` 스테이지 수 이상의 번호 → `STAGE 8/8`로 보정

화면 배치·글꼴 적용·그림 표시는 Phaser와 브라우저가 있어야 확인되므로 자동 테스트로 다루지 않는다. 이 저장소의 테스트는 지금까지 Phaser에 의존하지 않는 순수 로직만 다뤄왔고, 그 방침을 유지한다.

### 직접 플레이해서 확인 (`npm run dev`)

1. 타이틀에 하늘 파랑 배경, 지형 띠 그림, `Let's go!!` 제목이 뜨고 **글꼴이 픽셀 서체**다.
2. 죽으면 자주색 화면에 적·가시 그림이 뜨고, `STAGE N/8`의 N이 **실제로 죽은 스테이지**와 같다. (개발용 `?stage=5`로 들어가 죽어서 `STAGE 5/8`이 뜨는지 확인)
3. 마지막 스테이지를 깨면 진초록 화면에 월계관 고퍼가 뜬다.
4. **창을 아주 넓게, 아주 좁게 끌어본다.** 어느 폭에서도 글자가 화면 밖으로 넘치지 않고, 배경에 빈 틈이 생기지 않으며, 그림 비율이 찌그러지지 않는다.
5. 세 화면 모두에서 **배경음악이 지금처럼 흐른다.** 플레이 중에는 음악이 작아지고 효과음이 그 위로 들린다.
6. 세 화면의 조작이 그대로다 — 타이틀은 아무 키, 죽음은 `SPACE`/`ENTER`/클릭으로 재시도·`ESC`로 메뉴, 클리어는 `SPACE`/`ENTER`/클릭으로 다시 시작·`ESC`로 메뉴.

## 11. 금지사항

- 그림 파일에 배경색을 칠하지 **말 것** → 배경은 코드가 화면 전체에 칠한다. 창 비율이 변하기 때문이다.
- 시안 PNG를 자동 벡터 변환에 넣지 **말 것** → 도형을 나열해 새로 작성한다. 시안에는 기기 테두리와 설명 글자가 섞여 있다.
- 그림 크기를 화면 크기에 맞춰 곱해서 파일에 적지 **말 것** → 파일은 논리 크기로 적고, 화면 배율은 배치할 때 곱한다.
- SVG 루트의 `width`/`height`를 빼먹지 **말 것** → Phaser가 이 값으로 크기를 계산한다.
- 시안에 있다고 해서 점수·설정·기록 화면을 만들지 **말 것** → 이번 범위 밖이다. 없는 기능을 안내하는 문구도 넣지 않는다.
- 글꼴이 도착하기 전에 게임을 시작하지 **말 것** → 첫 화면이 기본 글꼴로 그려진 채 굳는다.
- 게임 안(스테이지 플레이)의 그림·수치·소리를 건드리지 **말 것**.

## 12. 고려사항

- **시안과 실제 화면의 비율이 다르다.** 시안 타이틀은 아이패드 틀이라 거의 정사각(1.04 : 1)인데, 실제 게임은 1.58~2.04 : 1로 훨씬 납작하다. 그래서 타이틀의 세로 간격은 시안보다 압축했다. 죽음·클리어 화면의 시안(약 816×540, 736×540)은 실제 비율과 거의 같아 그대로 옮길 수 있다.
- **글꼴 소문자 모양.** 픽셀 글꼴은 대문자 위주로 설계된 경우가 많아 `Let's go!!`의 소문자가 어색할 수 있다. 글꼴을 받아 실제로 확인하고, 어색하면 보고한 뒤 대안을 상의한다. 임의로 대문자로 바꾸지 않는다.
- **제목과 안내문의 의미가 겹친다.** `Let's go!!`와 바로 아래 `press any key to start`가 비슷한 말이 됐다. 일단 그대로 두고, 실제 화면에서 어색하면 안내문을 짧게 줄이는 것을 제안한다.
- **색이 두 곳에 존재한다.** 고퍼 파랑 같은 색은 `COLORS`에도, 그림 파일에도 적힌다. 서로를 가리키는 주석으로 막지만 완전히 없앨 수는 없다. 게임 안의 고퍼 색을 바꾸는 작업을 할 때 이 화면들도 함께 확인해야 한다.
- **화면 도우미의 이름이 바뀐다.** `centredTextScreen` → `centredScreen`, `textScreen.ts` → `screen.ts`. 글자 전용이 아니게 되므로 이름을 맞춘다. 부르는 곳이 세 군데뿐이라 위험은 낮다.

## 13. 제약사항

- **세로 540은 고정이고 가로만 854~1100으로 변한다.** 모든 배치는 이 안에서 성립해야 한다.
- **Phaser는 SVG를 벡터로 유지하지 않는다.** 불러올 때 정한 크기로 한 번 굽는다. 창을 아주 크게 키우면 그림이 조금 부드러워질 수 있고, 이는 게임 안의 그림도 이미 받아들이고 있는 절충이다.
- **글꼴 라이선스.** 자유 사용 라이선스 글꼴만 쓰고, 라이선스 파일을 함께 둔다.
- **새 화면(씬)을 만들지 않는다.** 기존 세 화면만 고친다. (새 화면을 만들면 배경음악 켜기·끄기를 반드시 호출해야 하는 규칙이 걸린다.)
- **인터넷에서 글꼴을 실시간으로 불러오지 않는다.** 파일을 저장소에 포함해 오프라인에서도 동작하게 한다.

## 14. 범위 밖 (보고만 하고 손대지 않음)

- 점수 시스템, 설정 화면, 최고 기록 — 시안에는 있지만 이번에 만들지 않는다.
- 모바일 쓸어넘기기 조작 — 시안의 `SWIPE` 안내에 해당한다. 현재 게임은 화면을 누르는 조작만 지원하므로 `TAP`만 안내한다.
- 게임 안(스테이지 플레이) 화면의 그림.
- 화면 전환 효과(페이드 등).
